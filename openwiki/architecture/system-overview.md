# Culler system architecture

Culler is a local-first orchestration system for AI coding agents with one human operator. It deploys onto one Mac and runs unattended. This page describes the processes that make up a deployment, the single path by which they reach shared state, and the layout of the deployment directory `MC_HOME`.

Stated intent for the project as a whole lives in `VISION.md` (the current productionization work order) and `AGENTS.md`. The behavior below is taken from code unless marked as stated intent.

## One state store, one writer

The spine stores Culler operational records in one SQLite database. Host configuration, credentials, source repositories, and artifacts use their separate storage boundaries. The spine is the message bus and the ground truth for every Project, task, run, lease, and activity record. Its schema is in `mc/substrate/schema.sql` (plus `delivery.sql` and `environments.sql`); see [The spine: SQLite substrate and schema](spine-and-substrate.md).

The Go binary `mc` (`mc/cmd/mc`) is the only program that opens the spine. The package comment on `mc/cmd/mc/main.go` calls it "the sole spine writer" and pins the verb contract: one JSON object on stdout, diagnostics on stderr, exit 0 for success, 1 for a domain rejection, 2 for a usage or environment error. Every other component is a client of that contract. `AGENTS.md` makes this a hard rule: never open the spine from TypeScript.

This design keeps every state rule in one place. Triggers and CHECK constraints in the schema, plus the Go `mc/domain` layer, decide what is legal. A TypeScript bug cannot write an illegal row because TypeScript cannot write a row at all.

## Process topology

A production deployment has these processes:

| Process | Source | Runs where | Role |
| --- | --- | --- | --- |
| `mc` | `mc/cmd/mc` | Host (darwin), helper container, agent containers | Owns dispatch, control, and the spine |
| Resident | `resident/src/main.ts` | Host, under Bun, supervised by launchd | Tick loop, effect execution, repository, environment, trace, and wiki lanes |
| Dashboard | `dashboard/src/main.ts`, `dashboard/src/server.ts` | Host, under Bun, supervised by launchd | Operator web UI on `127.0.0.1:7333` |
| AgentsView | pinned release, `mc/deployment/agentsview.json` | Host, supervised by launchd | Trace viewer |
| Helper container | image from `runner/image` | Docker | Holds the spine volume; runs delegated `mc` |
| Agent containers | `runner/agent-runner`, `runner/collie-runner`, `runner/setup-runner` | Docker | Pipeline runs, Scribe runs, Collie sessions, and setup operations |
| Repository containers | `mc-land` in the runner image | Docker | Merge-candidate preparation and merge |

The launchd units are generated by `mc/deployment/supervision.go`. The resident and dashboard plists start `bun` on `resident/src/main.ts` and `dashboard/src/main.ts` with a JSON config each. Unit labels have the form `com.culler.<suffix>.<unit>` (`UnitLabel` in `mc/deployment/agentsview_supervision.go`), where the suffix is derived from the canonical `MC_HOME`. AgentsView is the third unit.

## How components talk to mc

Every client spawns `mc`, passes arguments and optional stdin, and reads one JSON object back. The resident also uses a private dispatch control channel.

- **Dashboard.** `dashboard/src/mc.ts` is the single seam to the spine. `makeMcRunner` spawns the configured `mc_bin` with the live environment, parses stdout as one JSON object, and returns the exit code and stderr. `dashboard/src/api.ts` passes HTTP requests to `mc` and returns the results with no cache and no durable state. See [Dashboard](dashboard.md).
- **Resident.** `execMcVia` in `resident/src/resident-control.ts` wraps the host `mc`. Ordinary verbs go through `execPlain`. `mc dispatch` is special: the resident opens a Unix socket pair, passes one end to the child on fd 3, and serves a control exchange on it. Inside `mc`, `brokerDispatch` (`mc/cmd/mc/resident_control.go`) reads that descriptor and sends a `hello` frame with the release build id, the control version, the spine schema id, the config schema version, and the deployment UUID. The resident refuses a hello that differs from its own expected values. `mc` then asks the resident for Collie inventory and pipeline liveness before it prepares and commits a dispatch. See [Resident](resident.md) and [Dispatch and the tick loop](../workflows/dispatch-and-tick-loop.md).
- **Runners.** Inside an agent container, `runner/agent-runner/main.ts` reads the launch envelope at `/mc/run.json`, installs the run's skills, starts one harness adapter, and spawns `mc heartbeat <run_id>` immediately and then every `heartbeat_interval_s`. Role terminals such as `mc complete` also go through `mc`. See [Runners](runners.md).

## Reaching the spine: the helper container

The spine lives in a Docker named volume, not on a host path. On macOS the host `mc` cannot open the file, because the bytes live inside the container runtime's Linux VM. The production `mc` therefore delegates: when `runtime.GOOS` is `darwin`, `shouldDelegateToHelper` in `mc/cmd/mc/runtime_scope_prod.go` returns true, `ensureRuntimeHelper` creates or repairs the helper container, and `delegate` in `main.go` re-runs the same argv as `docker exec -i <helper> mc …`. Stdin, stdout, stderr, and the exit code pass through unchanged.

The helper name and the volume name come from `deployment.RuntimeNames` (`mc/deployment/names.go`): a SHA-256 of the canonical `MC_HOME` yields a 12-hex suffix, giving `mc-helper-<suffix>` and `mc-spine-<suffix>`. Two deployments therefore cannot address each other's helper or spine. The helper runs `/bin/sleep infinity` as uid 10002 with no network, all capabilities dropped, and only the spine volume mounted at `/mc/spine`. Details are in [The mc CLI, verb scope, and boundaries](mc-cli-and-verb-scope.md).

Some verbs never delegate. `health`, `logs`, `config`, `routing`, and other host-file readers run locally because they read files under the host `MC_HOME`; `health` must answer even when Docker is down. `__uninstall` runs on the host because it removes the helper.

## Agent containers and identity

The resident applies each spawn effect in `resident/src/effects.ts`. It writes the launch envelope to `MC_HOME/runs/<run_id>.json` and binds it read-only at `/mc/run.json`. The container runs as uid 10002 with `--cap-drop ALL`. The spine volume is mounted in the container, but uid 10002 cannot open it. Only the setuid `mc` in the image (`/opt/culler-runtime/libexec/mc-real`, owned by uid 10001) can reach the spine. The presence of `/mc/run.json` is what tells `mc` that the caller is an agent and not the host, so the envelope is the run's identity and its verb scope.

The Project image supplies development tools. A separate runtime volume supplies Culler executables and runner files.
The selected Project image survives a Culler update.
Setup operations prepare and assess the Project before source acceptance.
Setup and pipeline containers share one persistent home per Project through `HOME=/home/agent`.
Each container receives separate temporary role directories within that home.
The source workspace remains fresh at its assigned commit.
The shared `/cache` volume holds disposable dependency files; removal preserves the Project home.
`resident/src/environment-lane.ts` defines these mounts, and `mc/verbs/onboardworkspace.go` prepares the host home.
See [Project environments](../workflows/project-environments.md).

The Scribe uses a separate repository and holds no Project lease.
Scheduled wiki updates merge only wiki changes into `main`, without a task review packet.
The task pipeline contains Worker, Verifier, and Packager steps.

## MC_HOME layout

`MC_HOME` defaults to `~/.culler` (`mcHomeDir` in `mc/verbs/ops.go`; `configuredCanonicalHome` in `mc/cmd/mc/canonical_home.go` also resolves symlinks). Notable entries, as used by the code:

| Path | Purpose |
| --- | --- |
| `config.toml` | Operator configuration (`mc/config`) |
| `routing.md` | Role-to-runtime routing table (`mc/routing`) |
| `deployment.uuid` | Host mirror of the spine's deployment identity (`mc/verbs/onboard.go`) |
| `runs/<run_id>.json`, `runs/<run_id>.mounts.json` | Launch envelope and host-only mount plan per run |
| `runs/repositories/<run_id>/repo` | Isolated repository of a Worker run, bound at `/workspace/source` (per `AGENTS.md`) |
| `runs/wiki-repositories/<run_id>/repo` | Isolated source for a Scribe wiki update |
| `environment-runs/` | Setup operation files and native sessions |
| `project-secrets/` | Protected Project secret values |
| `sessions/<run_id>` | Trace-only session folder, bound at `/mc/session` |
| `logs/` | NDJSON logs: `resident.ndjson`, per-run logs under `logs/runs/`, launchd stdout and stderr files |
| `agentsview/traces/`, `agentsview/token` | Trace copies for AgentsView and its API token |
| `state/projects/<project>/home` | Persistent Project dependency caches, tools, and tool configuration, bound at `/home/agent` |
| `state/wiki-key` | Secret prefix for wiki viewer paths |
| `backups/` | Spine snapshots written by `VACUUM INTO` |
| `bun/<version>/` | Pinned host Bun for published installations |
| `updates/transaction.json` | Durable update transaction and recovery phase |
| `supervision/`, `release/`, `bin/` | Generated launchd bundle, shipped release files, AgentsView executable |

The spine itself is not in `MC_HOME` in production. Its fixed path inside the helper and agent containers is `/mc/spine/spine.db`.

## Build variants

Two Go build tags change topology for tests. `test_fake_routing` replaces the production scope functions with environment-driven ones (`mc/cmd/mc/runtime_scope_testfake.go`): `MC_SPINE` names a directly reachable spine and `MC_HELPER` names a helper to delegate to. It also adds the deterministic `fake` harness family to routing. `test_scratch_spine` lets a Linux test build open a test database on any filesystem by disabling the Linux filesystem guard. Production builds carry neither tag. See [Checks and test lanes](../tests/checks-and-test-lanes.md).

## Optional Discord connection

The resident owns Discord network access through `discord-config.ts` and `discord.ts`.
The dashboard supplies **Configs → Discord**; host `mc` commands own its saved policy and spine projection.
The local `MC_HOME/discord.socket` carries configuration requests to the resident with owner-only access.
The generated supervision bundle contains no bot token.

A connection serves one server and one channel for authorized Collie conversations and selected alerts.
The resident consumes account confirmation codes before ordinary conversation handling.
Connection changes require host authority and apply without a process restart.
The [Discord guide](../integrations/discord.md) traces setup, account approval, replacement, and retirement across these components.
