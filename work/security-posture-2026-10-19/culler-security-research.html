The current design protects host files and control state better than it protects credentials and outbound data. Container isolation alone cannot prevent those disclosures.

OAuth is a token authorization protocol. Its access tokens authorize requests; its refresh tokens obtain new access tokens.

  1. Add an authenticated credential proxy and enforce its network path. Start with static provider keys. Keep the proxy outside agent containers.
  2. Keep the harness sandboxes disabled under the current architecture. Their privilege restrictions conflict with the protected mc executable.
  3. Keep Homie’s Project context and exclude credential files. Use a host-controlled file view across the same Projects and useful traces.

Controls that already exist

  • Container execution: agent processes use user identifier 10002, drop all Linux capabilities, and receive resource limits.
  • Protected runtime: Culler mounts its runtime and run identity read-only. Project image checks reject extra setuid files and file capabilities.
  • Protected state: the mc executable enters user identifier 10001. Its role checks use the fixed run identity.
  • Credential separation: real OAuth refresh tokens remain on the host. Codex receives access tokens and a dummy refresh token.
  • Browser access: the dashboard requires a bearer token, including on loopback. Host and Origin checks reject foreign hosts.
  • Untrusted reports: report frames omit script and same-origin permission. AgentsView uses a separate origin and temporary access grants.
  • Release controls: actions use commit pins. Pull request jobs have read-only permissions. Release inputs use checksums and image digests.

Three different proxy functions

  1. Transport: a forward proxy carries traffic. It can carry OAuth sign-in traffic and static-key traffic.
  2. Credential injection: a trusted service adds an application programming interface (API) credential to an approved request.
  3. Network enforcement: container network rules prevent direct connections that bypass the proxy.

Hypertext Transfer Protocol (HTTP) proxy variables only configure clients that obey them. Agent code can ignore those variables.

HTTP Secure (HTTPS) uses Transport Layer Security (TLS). An HTTPS CONNECT tunnel preserves that encryption and cannot change the encrypted Authorization header.

Credential injection needs an explicit API gateway or trusted TLS termination. Prefer an explicit gateway where the harness supports a custom endpoint.

For general TLS interception, the container must trust a certificate authority. Certificate pinning and some clients can prevent that approach.

Project variables and secrets today

Culler already distinguishes ordinary variables from secret references. The resident reads referenced secret files and sends values through container standard input.

The runner then places the selected values in process environments. The setup, agent, and both scopes control that selection.

This reduces accidental exposure in configuration records and container arguments. A selected secret remains readable by the process that receives it.

Approved serviceReal credential arrives here.
  • The resident manages a separate gateway process or container. Agent containers receive no upstream secret.
  • Each grant identifies one run and its allowed services. Run termination revokes the grant.
  • Network rules permit only the gateway and explicit Project services. Cover Internet Protocol versions 4 and 6, plus Domain Name System (DNS) traffic.
  • The gateway refuses private network addresses, host services, and metadata endpoints unless the Project explicitly requires them.
  • The gateway rechecks redirects and resolved addresses. It records metadata without credentials or request bodies.
  • Package downloads use a separate policy. Prefer dependency preparation before the agent receives useful credentials.

A proxy protects credentials only within its contract. An agent can still misuse an allowed service or send source text through an allowed provider.

Design recommendation. OpenAI’s environment guidance also separates credentials from untrusted execution.

This is nested process isolation, not necessarily another Docker container

The harness sandboxes apply operating-system restrictions to tool processes. Current Linux documentation describes Bubblewrap for both harnesses.

Culler’s older Codex comment describes Landlock and seccomp. That comment does not establish the internals of every current Codex version.

The important conflict is no_new_privs. This Linux restriction prevents an executed file from gaining privileges through its setuid bit.

  1. Culler starts the agent with user identifier 10002.
  2. The protected mc-real executable uses setuid to enter user identifier 10001.
  3. That identity permits access to the protected spine database.
  4. An inner sandbox that sets no_new_privs prevents this identity change.

The identity change grants database access, not root access. Culler intentionally omits Docker’s no-new-privileges option for agent containers.

Claude also documents a separate nested-container issue with the /proc mount. Its weaker nested mode does not resolve Culler’s setuid design.

Evidence: runner/image/runtime.Dockerfile:55–56; resident/src/effects.test.ts:1861. Sources: Codex sandbox; Claude Code sandbox.

Recommendation: preserve the current setting, then remove the architectural conflict

Do not enable the inner sandboxes as a simple configuration change. First replace in-container privilege elevation with an authenticated command service outside the agent.

The service can expose the existing role commands through a narrow remote procedure call interface. The agent container then needs no spine database mount.

  1. Bind each service credential to one run, role, and Project.
  2. Preserve the current identity, lease, and command authorization checks in the service.
  3. Remove the setuid dependency and spine mount from agent containers.
  4. Enable no-new-privileges on the outer container.
  5. Test the exact pinned harness versions with their inner sandboxes enabled.

Keep the existing container restrictions during that work. Additional sandbox layers can reduce damage, but each layer needs a demonstrated permission boundary.

Acceptance checks for that change
  • Each role can complete its permitted commands in a fresh session and a resumed session.
  • A run cannot submit another Project’s identity or use an expired credential.
  • Dependency preparation, browser tools, and artifact submission work under the selected restrictions.
  • Agent commands cannot read upstream credentials or open the spine directly.
  • A failed service connection stops the operation instead of enabling broader access.

Release priorities

These priorities reflect the reviewed attack paths. They are not vulnerability scores or estimates of exploitation frequency.

Before release: authenticate the Codex refresh broker

High priority · Confirmed endpoint behavior · Moderate effort

The endpoint checks the request shape but authenticates no caller. A request with an arbitrary refresh token receives a newly minted access token.

One listener serves one credential source. The projector exposes its address through host.docker.internal.

Any process that reaches the endpoint can request that account’s access token. A local process needs no knowledge of a real refresh token.

Removal of the broker address from shell environments does not authenticate callers.

The source also intends container access. I did not repeat the live Docker Desktop reachability check during this review.

Fix: require an unguessable grant for one run, with expiry and revocation. Reject absent, foreign, and expired grants before token refresh.

Use an authorization header where the harness supports one. Otherwise use a protected run-specific capability path and redact it everywhere.

Also add request limits and Cache-Control: no-store. A grant prevents unrelated callers; it does not protect against its authorized agent.

resident/src/refresh-broker.ts:32–82; credential-projector.ts:599–617; refresh-broker.test.ts:69–73. The synthetic-token test passed.

Define Homie’s file policy and preserve its Project context

High priority · Confirmed mount design · Exposure depends on local files

An ordinary Homie session receives all available Project roots and all session traces. The Vision-specific session narrows its Project roots.

A full Project mount can expose readable, untracked files such as .env. A read-only mount still permits their contents to leave the container.

The blocked-path policy checks source addresses. It explicitly does not scan directory contents.

Proposal: keep all available Projects and useful traces. Replace direct folder mounts with a host-controlled view that excludes declared credential files.

Preserve tracked local edits and explicitly included untracked source. Homie still reads source across Projects; the file policy cannot detect every secret.

resident/src/effects.ts:320–323, 548–559; mc/boundary/blocked.go:95–97. This is a source-based exposure assessment, not a claim that I found a secret.

Before release: remove assumptions about secret isolation

High priority · Confirmed credential projection · Small policy changes, larger technical fix

Static provider keys enter the container unchanged. OAuth access tokens also enter it. Project secret references become process environment values.

Use dedicated development accounts and the narrowest available permissions. Set provider spend limits and keep production credentials outside Project environments.

State that dependency commands and agent commands can read credentials in their process environment. Redaction limits accidental disclosure only.

Technical fix: move static provider keys behind the credential gateway. Extend support to OAuth after the protocol tests pass.

resident/src/credential-projector.ts:654–675; runner/shared/project-environment.ts:66–91.

Low effort: add the public security contract and automated scans
  • Add SECURITY.md with a private disclosure route, supported versions, and response expectations.
  • Document one trusted operator, readable data, network access, and the limits of prompt-injection defenses.
  • Scan the full Git history and release archives for secrets before publication. Rotate real credentials that appear in history.
  • Add dependency vulnerability checks for Go, Bun, Node.js, and container packages to continuous integration (CI).
  • Add automated dependency update proposals. Preserve exact version pins and the current credential-free pull request jobs.

Low to moderate effort: strengthen browser and data controls
  • Expand the dashboard Content Security Policy beyond frame-src 'self'. Restrict scripts, connections, embedding, objects, and base URLs.
  • Test exact Origin checks, including ports. Keep bearer authorization on every state request.
  • Review the durable dashboard token in browser local storage. A script injection could steal it; this review found no such exploit.
  • Add explicit token rotation and logout behavior. A host session cookie can reduce token exposure to scripts, with request-forgery protection.
  • Validate permissions on credential and secret files. Keep secrets out of ordinary variables, traces, backups, and generated review artifacts.
  • Test processor, memory, process, disk, and log limits. The reviewed launch code already limits the first three.

Substantive work: enforce outbound network policy

Real agent containers use Docker’s default network path. The launch code provides no destination allowlist or host-service exclusion.

Restrict direct outbound traffic outside the agent process. Proxy environment variables alone cannot enforce this policy.

  • Start with explicit provider, package registry, and Project service destinations.
  • Block other host services, private network addresses, and cloud metadata addresses.
  • Test proxy bypass through raw sockets, alternate DNS, Internet Protocol version 6, redirects, and address changes.
  • Separate dependency preparation from credentialed execution where feasible.
  • Define an explicit unrestricted mode with accurate disclosure of its access.

resident/src/environment-lane.ts:42–49; resident/src/effects.ts:529, 650, 1050–1053.

Substantive work: reduce trusted code and verify releases
  • Replace the in-container setuid path with the authenticated command service described in the Sandboxes section.
  • Separate inference credentials from repository tools through separate processes with enforced identities, or separate containers.
  • Require specific approval for external side effects and changes to authority. Prompt instructions cannot enforce those restrictions.
  • Add verifiable release signatures, build provenance, and a software bill of materials.
  • Consider a separate virtual machine or host for mutually untrusted Projects. Ordinary containers share the Docker host kernel.
  • Add malicious-repository tests for cross-Project reads, credential access, control-command abuse, and trace disclosure.

Checksums detect mismatched bytes. A checksum from the same compromised source cannot independently establish publisher identity.

Design recommendations. Current release evidence: .github/workflows/release.yml; install.sh:166–169. I found no explicit release signature verification in those paths.

Three comparison details matter

  • OpenClaw’s secret proxy has limited scope. Its automatic integration excludes sandbox commands, remote node commands, and provider-native harness subprocesses.
  • Hermes’s proxy protects selected environment credentials. It does not protect arbitrary mounted credential files or a compromised host process.
  • Neither proxy is a complete network boundary. Both projects document limits when a process ignores the proxy and opens raw sockets.

OpenClaw scope and limits · Hermes scope and limits.

What to adopt: explicit secret access modes, authenticated grants, a deployment security report, and clear public threat-model documentation.

What to prove independently: actual packet restrictions, isolation between Projects, and the scope of each credential grant.
